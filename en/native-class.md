# Native Classes

A Native Class is an independent object model that TypePHP provides for extreme-performance scenarios. With `#[Native]`, the class is compiled into a C++ object with a fixed field layout; properties access fields directly, and resolved method calls go directly into the `php_*` functions generated by TypePHP.

Native classes are not registered with ZendVM and do not create a `zend_class_entry`, Zend Object, dynamic property table, or Reflection metadata. It is not an automatic optimization mode for ordinary PHP classes, but a static type that the developer actively chooses, with stricter feature boundaries.

## First Native Class

```php
#[Native]
class Point
{
    public int $x = 0;
    public int $y = 0;

    public function __construct(int $x, int $y)
    {
        $this->x = $x;
        $this->y = $y;
    }

    public function sum(): int
    {
        return $this->x + $this->y;
    }
}

function move(Point $point, int $x, int $y): void
{
    $point->x = $x;
    $point->y = $y;
}

function main(): void
{
    $point = new Point(10, 20);
    move($point, 30, 40);
    echo $point->sum(); // 70
}
```

`#[Native]` lives in the root namespace and follows the name resolution rules of [Compile-Time Attributes](compile-time-attributes.md). This attribute can only be used on a named class, not on anonymous classes, Interface, Trait, or Enum.

## Performance Model

The hot path of a native class has deterministic cost:

- The object variable is a native pointer;
- `$a = $b` only copies the pointer, not the object;
- Property reads/writes are C++ field accesses at fixed offsets, without property name lookup;
- Methods continue to use TypePHP's function-style ABI, with the first parameter being the resolved `this` object;
- Resolved method calls do not go through `zend_call_function()`;
- visibility, types, and Interface contracts are checked at compile time wherever possible;
- No dynamic boxing, Reflection, or hidden ZendVM fallback.

Native classes are suitable for large numbers of small objects, object graphs, computational models, and high-frequency property access. When Reflection, dynamic properties, serialization, or handing objects to ordinary PHP extensions are needed, continue to use ordinary classes.

## Property Declaration and Default Values

Every instance property must declare its type explicitly:

```php
#[Native]
final class RequestContext
{
    public bool $ready = false;
    public int $status = 0;
    public float $elapsed = 0.0;
    public string $method = '';
    public array $headers = [];
    public object $request;
    public Stream $body;
    public mixed $metadata = null;
}
```

Properties without a written default value use a deterministic zero value, rather than the uninitialized state of PHP typed properties:

| Property type | Initial value |
|---|---|
| `bool` | `false` |
| `int` / `float` | `0` / `0.0` |
| `string` | empty string |
| `array` | empty array |
| `mixed` / `any` | `null` |
| Zend Object, Native Object | null pointer |
| `Stream` | empty resource state |

Supported types are bool, int, float, string, array, object, resolved ordinary classes, other Native Classes, Stream, mixed/any, valid non-Native union/nullable types, and BigInt, BigFloat, Decimal.

The following types cannot be used as native class properties:

- `Box`;
- `std::array`, `std::vector`, `std::map`, `std::orderedMap`, and other Std containers;
- `void`, `never`, `callable`, and other types that PHP property declarations themselves disallow;
- `readonly` properties and readonly classes.

Std containers can hold concrete Native Class objects in function locals, but cannot be embedded in native class properties. Ordinary PHP arrays cannot hold Native Objects.

### Property References

Only properties explicitly declared as `any` may take a reference:

```php
#[Native]
class Holder
{
    public any $dynamic = null;
    public string $name = '';
}

$ref =& $holder->dynamic; // allowed
$ref =& $holder->name;    // compile error
```

Even though string, array, object, or mixed have a PHPX wrapper layer underneath, they cannot take a reference; dynamic code might write another type through the reference, breaking the fixed field constraint. Native Object variables themselves also cannot take a reference, because object variables already have shared identity semantics.

## Object Identity, null, and clone

Native Objects preserve the identity semantics commonly used with PHP objects:

```php
$a = new Point(1, 2);
$b = $a;
$b->x = 10;
echo $a->x; // 10

$copy = clone $a;
$copy->x = 99;
echo $a->x; // 10
```

`$a = $b` does not copy the entity; `clone` performs a shallow field copy and calls `__clone()` if present.

`unset($object)` and `$object = null` only clear the current variable slot; they do not clear the real object and do not affect other aliases. Calling a method on a null pointer throws an `Error`. `?NativeClass` uses a null pointer to represent null and supports the nullsafe `?->` on pure Native chains.

Conditional expressions only check whether the object pointer is non-null, and do not call `toBool()`:

```php
if ($point) {
    // only means $point is not null
}
```

`===` and `!==` compare object identity, and also support comparison with `null`. `==`, `!=`, size comparisons, arithmetic, and bitwise operations have no reliable Zend object semantics, so they produce compile errors; when value equality is needed, declare an explicit ordinary method.

## Parameters and Return Values

Native Objects can only be passed via an explicit Native Class type:

```php
function required(Point $point): Point
{
    return $point;
}

function optional(?Point $point): ?Point
{
    return $point;
}
```

`Point $point` is guaranteed non-null at function entry; only `?Point $point` allows null. Parameters are passed by pointer value; modifying the object is visible to the caller, while reassigning the local parameter does not replace the caller's variable slot.

The following signatures are not supported:

- Native Object parameters or return values using `&`;
- Native Object variadic parameters;
- unions or intersections containing a Native Class;
- carrying a Native Object with `mixed`, `object`, or Interface.

A Native Object can only be passed to functions/methods that TypePHP can resolve statically and whose parameter is explicitly declared as the same Native Class or its Native base class. It cannot be passed to ordinary PHP functions, extension functions, anonymous functions, or dynamic callables.

## Inheritance, Trait, and Interface

Native classes support single inheritance, abstract classes, abstract methods, final, and method overriding. Both the parent and child classes must explicitly declare `#[Native]`; native classes and ordinary ZendVM classes cannot inherit from each other:

```php
#[Native]
abstract class Shape
{
    abstract public function area(): float;
}

#[Native]
final class Rectangle extends Shape
{
    public float $width = 0.0;
    public float $height = 0.0;

    public function area(): float
    {
        return $this->width * $this->height;
    }
}
```

When inheritance relationships require dynamic dispatch, TypePHP generates a limited C++ virtual thunk; the method body is still an ordinary `php_*` function. PHP does not support declaring multiple methods of the same name in the same class distinguished by parameter signature, and native classes do not add C++-style method overloading either.

Trait injects properties, constants, methods, and Property Hook AST into the native class at compile time, which are then compiled like the class's own members.

Interface itself is still an ordinary PHP Interface and is registered with ZendVM. A native class can `implements` an Interface, and the compiler checks the method, signature, and Property Hook contracts, but this relationship only exists at compile time:

```php
#[Native]
class NativeCounter implements Countable
{
    public function count(): int
    {
        return 1;
    }
}

$counter = new NativeCounter();
echo count($counter); // directly calls NativeCounter::count()
```

A Native Object cannot be assigned or passed as an Interface type, and ZendVM's Reflection cannot see this implementation relationship. When polymorphic parameter passing is needed, use a common Native base class; when implementation reuse is needed, use a Trait.

## Iterator and ArrayAccess

Implementing `Iterator` or `IteratorAggregate` makes the class directly usable in `foreach`. TypePHP converts the loop into corresponding method calls at compile time:

```php
#[Native]
class RangeIterator implements Iterator
{
    public int $position = 0;
    public int $limit = 0;

    public function __construct(int $limit) { $this->limit = $limit; }
    public function rewind(): void { $this->position = 0; }
    public function valid(): bool { return $this->position < $this->limit; }
    public function current(): int { return $this->position; }
    public function key(): int { return $this->position; }
    public function next(): void { $this->position++; }
}

foreach (new RangeIterator(3) as $value) {
    echo $value;
}
```

Native Objects that do not implement Iterator/IteratorAggregate cannot be `foreach`-ed; TypePHP does not enumerate public properties like ordinary PHP objects. Reference iteration is also not supported.

After implementing `ArrayAccess`, reads, assignments, appends, `isset()`, `empty()`, `??`, and `unset()` map directly to `offsetGet/offsetSet/offsetExists/offsetUnset` calls. To avoid ambiguous reference and temporary value semantics, indirect modification of elements is not supported, for example:

```php
$bag['count']++;          // not supported
$bag['count'] += 1;       // not supported
$bag['nested']['x'] = 1;  // not supported
$ref =& $bag['value'];    // not supported
```

## Property Hook and Generator Attributes

Native Classes support direct get/set of PHP 8.4 Property Hooks. Hooks become resolved method calls at compile time and do not go through Zend property handlers. Indirect writes, compound writes, taking references, and using `isset()`/`empty()` on a hook are not supported.

Attributes that rely only on compile-time AST generation, such as Getter, Setter, Constructor, Printer, and Arrayable, can act on Native Classes; the generated results enter Native Calls like hand-written methods. The specific combination limitations still follow the respective attribute pages.

`readonly` is not supported. PHP readonly relies on Zend property initialization state and runtime property handlers, which differs from the fixed field model of native classes.

## Type Conversion and Language Integration

Native classes do not call PHPX's dynamic keyword conversion helpers. The class must actually declare the corresponding zero-argument method, and the return type must match exactly:

```php
#[Native]
class Result
{
    public int $value = 0;

    public function toArray(): array { return ['value' => $this->value]; }
    public function toInt(): int { return $this->value; }
    public function toBool(): bool { return $this->value !== 0; }
    public function toString(): string { return (string) $this->value; }
}

$result = new Result();
echo (string) $result;
$json = json_encode($result->toArray());
```

Keyword methods such as `toArray()`, `toString()`, `toInt()`, `toFloat()`, and `toBool()` are supported. `__toString(): string` can serve as an alias for `toString()`; string casts, `strval()`, concatenation, and `echo` use the same rule. When the corresponding method is missing or the return type does not match, the compiler reports an error directly.

After implementing `Countable`, the single-argument `count($object)` maps to the resolved `count()` method call. `__invoke()` also supports resolved calls.

`json_encode()` does not accept Native Objects. Explicitly calling `toArray()` first clearly shows the object graph conversion and memory allocation boundary.

## Lifecycle and GC

Native Objects do not use Zend reference counting or `std::shared_ptr`. TypePHP/PHPX uses an independent tracing GC to track Native Object fields, local variables, TypePHP global/static slots, and supported local Std containers, so objects can have circular references.

For the complete object layout, root frame, collection threshold, object resurrection, Fiber, and request shutdown flow, see [GC Mechanism: Tracing GC for Native Class Objects](gc.md#6-tracing-gc-for-native-class-objects).

The GC runs automatically and does not provide a collection interface that business code must call. `__destruct()` runs when an object becomes unreachable or at request shutdown, at most once per object; the inheritance chain runs from the most-derived class to the base class. Unlike PHP reference-counted objects, when the last variable leaves scope, immediate destruction is not guaranteed, and the destruction order among multiple unreachable objects is not guaranteed.

Therefore, do not rely on `unset($object)` to immediately close a file or commit a transaction. Resources that need deterministic timing should provide explicit `close()`, `commit()`, and similar methods, with `__destruct()` only as a final cleanup guarantee.

TypePHP globals and static locals can hold Native Objects; under ZTS they use request/thread-isolated native slots and are cleaned up at request shutdown. `$GLOBALS['name']` in the form of a literal or a compile-time evaluable string can map to the same slot; dynamic `$GLOBALS[$name]` does not support Native Objects.

## ZendVM Boundary and Unsupported Features

Native Objects have no zval representation. The compiler rejects them crossing the ZendVM boundary instead of silently boxing or degrading to ordinary objects. They cannot:

- be placed in an ordinary PHP array, ordinary object property, mixed/object variable, or Box;
- be passed to unknown PHP/extension functions, dynamic methods, dynamic callables, or `call_user_func()`;
- be captured into a Zend Closure, or used as a parameter, local variable, return value, `this`, or `yield` value of a TypePHP Generator;
- use Reflection, WeakReference, serialize, or be passed directly to `json_encode()`;
- be accessed in `eval()` or dynamic PHP code;
- use variable method names `$object->$method()`, dynamic properties, or dynamic class creation;
- use runtime class introspection such as `get_class()`, `get_parent_class()`, `get_called_class()`.

The following dynamic magic methods are also not supported:

- `__call()`, `__callStatic()`;
- `__get()`, `__set()`, `__isset()`, `__unset()`;
- `__sleep()`, `__wakeup()`, `__serialize()`, `__unserialize()`;
- `__set_state()`, `__debugInfo()`.

All these limitations report a FatalError at compile time. If the business needs these capabilities, use an ordinary class; do not treat native classes as an unconditional replacement for ordinary PHP objects.

## Selection Recommendations

Prefer ordinary classes; only convert clearly-bounded internal data structures to `#[Native]` when performance analysis confirms that object layout, property lookup, or dynamic dispatch is a hotspot.

Code suitable for native classes usually has the following characteristics:

- Objects only flow within TypePHP static code;
- Classes and call targets can be determined at compile time;
- Property reads/writes or method calls are very frequent;
- No reliance on Reflection, serialization, dynamic calls, and PHP extension object interfaces;
- Acceptable destruction timing of the tracing GC.

Whenever an object needs to enter PHP frameworks, extension functions, or dynamic APIs, an ordinary class is usually the more reliable choice.
