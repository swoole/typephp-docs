# Compiling to WebAssembly

TypePHP can compile PHP source code ahead of time into a WASI 0.2 (Preview 2) Component. PHP, PHPX, the TypePHP Runtime, and the high-precision arithmetic libraries are statically linked into the same `.wasm` file, so deploying the program does not require PHP on the target machine, nor any Linux `.so` shared libraries.

The same Component can run in two kinds of environments:

- **Wasmtime**: suitable for command-line tools, server-side tasks, and automated testing.
- **Browsers that support JSPI, such as Chrome**: the Component is first converted to ESM by Jco, then run through the WASI Host inside a Worker.

TypePHP supports only WASI 0.2, not WASI 0.1 (Preview 1). The current implementation is an NTS, single-threaded model.

## Building a Component First

Create `hello.php`:

```php
<?php

function main(): void
{
    echo "Hello TypePHP/WASI\n";
}
```

Run:

```bash
tpc --wasm hello.php
```

The bare `--wasm` is equivalent to `--wasm=component` by default and only generates:

```text
hello.wasm
```

Run:

```bash
wasmtime hello.wasm
```

Expected output:

```text
Hello TypePHP/WASI
```

A Component is the simplest way to get started and does not require Node.js or Jco.

### Using the Nano runtime

The default WASI build uses the prebuilt WASI SDK libraries supplied by PHPX.
Add `--nano` to select the VM-free PHP Nano source-composition build instead:

```bash
tpc --nano --wasm hello.php
wasmtime hello.wasm
```

Nano WASI currently supports command / `bin` projects only. It also supports
`--wasm=browser`, but not `mode: library`. It retains console I/O, arguments,
clocks, entropy, and local file access through preopened directories, while
excluding dynamic PHP, networking, sockets, and process execution. See
[Nano Native Compilation](nano.md) for the full boundary and Composer
dependencies.

## Environment Requirements

### Which Tools Need to Be Installed

The current version requires:

| Tool | Version requirement | Required | Purpose |
|---|---:|---|---|
| [WASI SDK](https://github.com/WebAssembly/wasi-sdk/releases) | 33 or higher | Yes | Provides LLVM/Clang/LLD 22 and the `wasm32-wasip2` toolchain |
| [Wasmtime](https://docs.wasmtime.dev/cli-install.html) | 47 or higher | Yes | Runs and tests WASI 0.2 Components |
| [Jco](https://bytecodealliance.github.io/jco/) | 1 or higher | Only for the `browser` profile | Converts Components to browser ESM |
| [wit-bindgen](https://github.com/bytecodealliance/wit-bindgen) | Pinned to `wit-bindgen-cli 0.60.0` | Only for `mode: library` | Generates Canonical ABI bindings for `#[WasmExport]` |
| [WABT](https://github.com/WebAssembly/wabt) | Latest stable recommended | No | Debugs the Core Wasm generated by Jco; not part of the TypePHP build |

Ordinary command components do not require Rust, Cargo, or `wit-bindgen`. Only when using `mode: library` / `#[WasmExport]` do you need to install the pinned version of `wit-bindgen-cli`. The PHPX release package only provides target-side headers and static libraries, and no longer ships the host-platform `wit-bindgen` binary.

The executables of the WASI SDK and Wasmtime must be on `PATH`. The browser profile also requires `jco`, and library mode also requires `wit-bindgen` on `PATH`. TypePHP does not probe fixed directories such as `/opt`, and has no WASI-specific toolchain environment variables.

The current TypePHP WASM build entry targets Linux and macOS; macOS requires Bash 4.0+ and `realpath` on `PATH` (a newer Bash and GNU coreutils can be installed via Homebrew). Windows users should currently build in WSL. The fact that WASI SDK, Wasmtime, Jco, or WABT themselves offer Windows versions does not mean the current TypePHP Windows toolchain supports WASM builds.

### Installing the WASI SDK

Download the 33-or-higher stable release matching your host operating system and CPU architecture from [WASI SDK Releases](https://github.com/WebAssembly/wasi-sdk/releases). Do not download the `Source code` archive that GitHub auto-generates.

On Linux x86-64 you can download the `.deb` and install it directly:

```bash
sudo apt install ./wasi-sdk-33.0-x86_64-linux.deb
export PATH="/opt/wasi-sdk/bin:$PATH"
```

Alternatively, on Linux or macOS, extract the matching `.tar.gz` and add its `bin` directory to `PATH`. For example, after extracting to `/opt/wasi-sdk-33.0`:

```bash
export PATH="/opt/wasi-sdk-33.0/bin:$PATH"
```

If it needs to take effect permanently, write the same directory into your shell configuration file. Windows/WSL users should install the Linux WASI SDK inside WSL and run `tpc` from WSL.

### Installing Wasmtime

On Linux and macOS you can use the [official Wasmtime installation script](https://docs.wasmtime.dev/cli-install.html):

```bash
curl https://wasmtime.dev/install.sh -sSf | bash
```

Reopen the terminal as instructed by the installer, or add `$HOME/.wasmtime/bin` to `PATH`.

### Browser Development: Installing Jco with npm

Only `wasm: browser` or `--wasm=browser` requires Jco. The simplest installation is a single npm command, with no Cargo needed:

```bash
npm install --global @bytecodealliance/jco
```

This command works on both Linux and macOS. npm's global executable directory must be on `PATH`; Node.js's standard installer usually configures this automatically.

If you want to pin the project's Jco version via `package-lock.json`, you can install it locally instead:

```bash
npm install --save-dev @bytecodealliance/jco
```

For a project-local install, it is recommended to run `tpc` from an npm script; npm automatically adds `node_modules/.bin` to the command's `PATH`. You can also add that directory to the current terminal's `PATH` manually. If npm is not installed yet, install [Node.js](https://nodejs.org/en/download) first.

For Jco's official usage and Component transpilation examples, see [Jco Example Workflow](https://bytecodealliance.github.io/jco/example.html).

### Verifying the Toolchain

Run:

```bash
wasm32-wasip2-clang++ --version
wasm32-wasip2-clang++ --print-target-triple
wasm-component-ld --version
wasmtime --version
jco --version  # only required for the browser profile
```

The target triple should be:

```text
wasm32-unknown-wasip2
```

The TypePHP build also checks `wasm32-wasip2-clang`, `llvm-ar`, `llvm-ranlib`, and `llvm-nm`. The browser profile checks `jco`, and library mode checks `wit-bindgen` and its exact version. If the version or target does not meet the requirements, an error is raised before compilation begins. WABT is not a build dependency of TypePHP, nor a substitute for the WASI SDK.

### Optional: Installing WABT to Debug Core Wasm

[WABT (WebAssembly Binary Toolkit)](https://github.com/WebAssembly/wabt) is a set of Core WebAssembly analysis tools. TypePHP, the WASI SDK, Jco, and Wasmtime do not depend on it; ordinary users can skip installing it.

When you need to analyze generated code, download the latest stable release matching your host OS and CPU architecture from [WABT Releases](https://github.com/WebAssembly/wabt/releases), extract it, and add its `bin` directory to `PATH`. For example, installing to `/opt/wabt-1.0.41`:

```bash
export PATH="/opt/wabt-1.0.41/bin:$PATH"
wasm-objdump --version
```

Common tools:

| Command | Purpose |
|---|---|
| `wasm-objdump` | Inspects sections, imports, exports, and instruction disassembly |
| `wasm2wat` | Converts Core Wasm to readable WAT text |
| `wasm-validate` | Validates the binary format and instruction types of Core Wasm |
| `wasm-stats` | Counts instructions, functions, and sections |
| `wasm-strip` | Removes name or other custom sections; TypePHP artifacts are usually already stripped |

The `app.wasm` output by TypePHP is a Component Model container, whereas WABT mainly targets Core Wasm. After the browser profile converts it with Jco, you can inspect the core module inside:

```bash
wasm-objdump -x generated/program.core.wasm
wasm2wat generated/program.core.wasm -o program.wat
wasm-validate generated/program.core.wasm
wasm-stats generated/program.core.wasm
```

Do not conclude that a TypePHP artifact is necessarily corrupt just because an old WABT cannot recognize new exception-handling instructions. The WABT in system package repositories may lag significantly behind the WASI SDK. When analyzing a full WASI 0.2 Component, prefer [wasm-tools](https://github.com/bytecodealliance/wasm-tools) or Wasmtime; WABT is better suited to analyzing the `program.core.wasm` that Jco splits out.

### TypePHP WASI Runtime Library

The TypePHP release package provides WASI static libraries and target-side headers bound to the compiler version. They are installed together in the PHPX directory:

```text
<PHPX_HOME>/wasm/
└── wasm32-wasip2/
    ├── include/
    ├── lib/
    │   ├── libphp.a
    │   ├── libphpx.a
    │   ├── libgmp.a
    │   ├── libgmpxx.a
    │   ├── libmpfr.a
    │   ├── libmpdec.a
    │   └── libmpdec++.a
    └── .typephp-wasi-sdk-abi
```

TypePHP locates PHPX in the following order:

1. The `PHPX_HOME` environment variable.
2. The `swoole/phpx` package directory installed via Composer.
3. `vendor/swoole/phpx` inside the current TypePHP installation directory.

To customize the PHPX location, just use the existing `PHPX_HOME`:

```bash
export PHPX_HOME=/opt/phpx
```

Do not specify or replace a single `.a` separately. These headers, static libraries, and the ABI marker must all come from the same TypePHP/PHPX release package; mixing versions can cause link errors or runtime memory issues.

Ordinary application builds do not recompile PHP, PHPX, GMP, MPFR, or mpdecimal, and do not require Autoconf, Bison, re2c, or the PHP source.

### How to Install wit-bindgen

`wit-bindgen` and Jco have different responsibilities: the former generates the C/C++ Guest bindings for the Wasm Component under `mode: library`, and the latter converts the already-linked Component into browser ESM. Therefore installing Jco cannot replace `wit-bindgen`.

Command-component users do not need to install `wit-bindgen`:

- `mode: bin` does not invoke it.
- `mode: library` must use `wit-bindgen-cli 0.60.0` from `PATH`.
- `tpc` validates the version before compiling; other versions are rejected to avoid generating a C ABI incompatible with the current adapter.

When using library mode, first install [Rustup](https://rustup.rs/), then run:

```bash
cargo install wit-bindgen-cli --version 0.60.0 --locked
wit-bindgen --version
```

The version output must be:

```text
wit-bindgen-cli 0.60.0
```

Cargo installs the host executable into the user's Cargo bin directory, usually `$HOME/.cargo/bin`. Confirm that directory is on `PATH`; a program targeted at Wasm cannot replace the host tool.

## Command-Line Modes

### Component Mode

The following two commands are equivalent:

```bash
tpc --wasm app.php
tpc --wasm=component app.php
```

The default output is `app.wasm` in the current directory. The generated C++ and object files are placed in TypePHP's default build directory, or you can specify one separately:

```bash
tpc --wasm app.php --build-dir build/wasm
```

Single-file WASM commands only accept the input file, the `--wasm` profile, and `--build-dir`. Project options such as the output path and source list should go into `project.yml`; the Host-mode command-line arguments like `-o`, `-O`, and `-j` cannot be reused. The WASI Runtime and generated code use release-build optimization settings.

### Browser Mode

Use it explicitly when you need browser artifacts:

```bash
tpc --wasm=browser app.php
```

This command first generates `app.wasm`, then invokes Jco to generate `app.browser/`. Therefore `jco` must be on `PATH`:

```bash
npm install --global @bytecodealliance/jco
```

The files in the browser directory are Jco-generated Component bindings, not a complete web page. The application still needs to provide the HTML, Worker, WASI Preview 2 Shim, and Host configuration for stdin, stdout, environment variables, the filesystem, and network capabilities. It is recommended to start from the `examples/wasm-hello` example in the TypePHP repository.

## Using project.yml

For multi-file projects, `project.yml` is recommended.

WASM supports the `bin`/`binary`/`cli` command modes, and also supports exporting WIT interfaces via `mode: library` and `#[WasmExport]`. It does not support generating PHP dynamic extensions.

### Wasmtime Project

```yaml
name: report-tool
mode: bin
wasm: component

sources:
  - src

build-dir: build
output: dist/report-tool.wasm
```

You no longer need to pass `--wasm` when building:

```bash
tpc project.yml
wasmtime dist/report-tool.wasm
```

### Browser Project

```yaml
name: browser-app
mode: bin
wasm: browser

sources:
  - src

build-dir: build
output: component/browser-app.wasm
wasm-browser-dir: generated
```

### Exporting Functions for JavaScript

When JavaScript needs to call TypePHP functions multiple times, use a library component:

```yaml
name: calculator
mode: library
wasm: browser
wasm-package: app:calculator@1.0.0
wasm-world: calculator

sources:
  - src

build-dir: build
output: component/calculator.wasm
wasm-browser-dir: generated
```

Use `#[WasmExport]` to mark the functions to publish:

```php
#[WasmExport]
function add(int $left, int $right): int
{
    return $left + $right;
}

#[WasmExport(name: 'greet-user')]
function greetUser(string $name): string
{
    return "Hello, {$name}";
}
```

JavaScript must first create the runtime, then call the exported methods:

```js
const component = await instantiate(null, wasi.getImportObject());
const runtime = await component.api.createRuntime();

try {
    console.log(await runtime.add(20n, 22n));
    console.log(await runtime.greetUser('TypePHP'));
} finally {
    runtime[Symbol.dispose]();
}
```

The current export ABI supports `bool`, `int`, `float`, `string`, the corresponding nullable types, and `void`. PHP `int` maps to `bigint` in JavaScript. Arrays and objects currently need to be encoded as JSON strings. For the complete type limitations, exception behavior, NTS serial-call rules, and ZendVM lifetime, see [`WasmExport`](wasm-export.md).

`wasm` can **only** be `component` or `browser`. The following configuration is invalid:

```yaml
wasm: true
```

`target-platform` usually does not need to be configured. As long as WASM is enabled, TypePHP defaults to:

```yaml
target-platform: wasm32-wasip2
```

If configured explicitly, only `wasm32-wasip2` or the equivalent `wasm32-unknown-wasip2` is accepted. The WASI Preview 1 targets `wasm32-wasi` and `wasm32-wasip1` are rejected.

All relative paths are resolved relative to the directory containing `project.yml`. The command line can temporarily override the output profile:

```bash
tpc project.yml --wasm=component
tpc project.yml --wasm=browser
```

## Running in Wasmtime

### Arguments and Environment Variables

TypePHP's `main()` can accept arguments:

```php
<?php

function main(int $argc, array $argv): void
{
    echo "argc={$argc}\n";
    var_dump($argv);
    var_dump(getenv('APP_ENV'));
}
```

Pass arguments and environment variables:

```bash
wasmtime --env APP_ENV=production app.wasm first second
```

The WASI Host is responsible for providing `$argc`, `$argv`, environment variables, and stdin/stdout/stderr.

### Filesystem

PHP streams and common file functions can access directories authorized by the WASI Host, such as `file_get_contents()`, `file_put_contents()`, `fopen()`, `scandir()`, and `mkdir()`.

WASI does not by default let a program access the entire host filesystem. Pre-open directories explicitly at runtime:

```bash
mkdir -p data
wasmtime --dir ./data::/data app.wasm
```

Use Guest paths in the program:

```php
file_put_contents('/data/result.txt', "generated by TypePHP\n");
$contents = file_get_contents('/data/result.txt');
```

Paths that are not authorized produce `No such file or directory` or permission errors. This is WASI sandbox behavior, not a PHP file function failure.

### HTTP/HTTPS GET

The WASI version supports making HTTP/HTTPS GET requests through PHP's synchronous `file_get_contents()`:

```php
<?php

function main(): void
{
    $context = stream_context_create([
        'http' => [
            'method' => 'GET',
            'timeout' => 10,
            'ignore_errors' => true,
        ],
    ]);

    $body = file_get_contents('https://www.example.com/', false, $context);
    if ($body === false) {
        fwrite(STDERR, "request failed\n");
        return;
    }
    echo $body;
}
```

Wasmtime needs to explicitly allow WASI HTTP:

```bash
wasmtime -S http app.wasm
```

Current HTTP stream limitations:

- Only GET and read-only streams are supported.
- `http.timeout` and `http.ignore_errors` are supported.
- The Curl API is not provided.
- Raw TCP/UDP sockets are not exposed.

The PHP API remains synchronous. Wasmtime blocks waiting for Host I/O; in browsers, JSPI suspends the Wasm call stack and waits for a Promise, without busy-waiting on the CPU.

### Time and Secure Random Numbers

The following capabilities are provided by the WASI Host, using the same set of PHP APIs in Wasmtime and browsers:

```php
$now = time();
$formatted = date('Y-m-d H:i:s T', $now);
$token = bin2hex(random_bytes(16));
$number = random_int(1, 1000);
```

## Running in the Browser

A browser cannot use `WebAssembly.instantiate()` directly to execute a WASI 0.2 Component. TypePHP's browser profile uses Jco to convert the same Component to ESM, and requires the browser to support:

- `WebAssembly.Suspending`
- `WebAssembly.promising`

These two JSPI APIs are used to suspend and resume the Wasm stack while synchronous PHP calls wait on asynchronous browser I/O.

It is recommended to run the complete example directly:

```bash
cd examples/wasm-hello
npm ci
npm run wasm
npm run dev
```

The example demonstrates:

- Arguments, environment variables, and standard input/output.
- `time()`, `date()`, `random_int()`, and `random_bytes()`.
- An in-memory filesystem plus optional OPFS snapshot persistence.
- `file_get_contents()` HTTP/HTTPS GET.
- The PHP extension list and the three high-precision types.

Browser network requests are still subject to CORS, CSP, and Mixed Content rules. The WASI HTTP capability does not bypass browser security policies.

The example runs TypePHP inside a dedicated module Worker. File operations happen on a synchronous in-memory filesystem; when persistence is enabled, the Worker restores and saves snapshots through OPFS at program startup and shutdown, avoiding an asynchronous JavaScript boundary crossing on every PHP file access.

The TypePHP application itself also registers a runtime module named after the project, so the actual result of `get_loaded_extensions()` usually includes a `typephp_*` entry as well; it belongs to the current application, not an extra PHP standard extension.

The program can obtain the actual loaded list:

```php
foreach (get_loaded_extensions() as $extension) {
    echo $extension, "\n";
}
```

WASI artifacts do not support loading `.so` or `.dll` dynamic extensions at runtime. Only the extensions statically compiled with the TypePHP WASI SDK are available.

## High-Precision Types

WASI artifacts include TypePHP's language-level high-precision types:

- `BigInt`: based on GMP.
- `BigFloat`: based on MPFR.
- `Decimal`: based on mpdecimal.

They are used the same way as native TypePHP:

```php
$big = std::bigInt('123456789012345678901234567890');
$decimal = std::decimal('199.95') * std::decimal('1.0825');
$float = std::bigFloat('3.1415926535897932384626433832795');

echo $big->toString(), "\n";
echo $decimal->toString(), "\n";
echo $float->toString(), "\n";
```

Wasm uses 32-bit pointers, but `zend_long` remains 64-bit. High-precision arithmetic keeps arbitrary-precision semantics, though without native-platform assembly optimizations, throughput may be lower than a native Linux build.

## Current Limitations

The WASI runtime environment is not equivalent to a full Linux. The following are currently not supported:

- Fibers and Generators, including `yield`.
- Process creation and management, such as `proc_open()`, `exec()`, `system()`, and `shell_exec()`.
- Backtick shell-execution syntax.
- Raw TCP/UDP sockets, as well as `stream_socket_*()`, `socket_*()`, and `fsockopen()`.
- `pcntl_*()`, `posix_*()`, and signal handling.
- Curl, MySQL, and other extensions not statically compiled into the WASI Runtime.
- Dynamically loading PHP extensions.
- Multithreading and ZTS.

For the APIs explicitly listed as limited — processes, shell, raw sockets, and signals — the compiler raises a Fatal Error after static recognition, avoiding the program degrading into a link error or producing different semantics in Wasmtime versus Chrome. PHP extensions not statically compiled into the Runtime are likewise unusable.

PHP exceptions and Zend bailout are still supported. Time, random numbers, standard streams, arguments, environment variables, authorized filesystems, and HTTP GET are provided by the WASI 0.2 Host.

The OpenSSL extension in WASI is built crypto-only, keeping encryption, decryption, digests, signing, keys, and certificate handling, and does not include the TLS stream transport. HTTP/HTTPS requests are provided by the WASI HTTP Component, independent of the OpenSSL extension. PDO SQLite supports in-memory databases and database files in pre-opened directories, but does not support loading SQLite dynamic extensions at runtime.

## Artifacts and Deployment

For Component-mode deployment, you usually only need:

```text
app.wasm
```

The target environment needs a Runtime compatible with WASI 0.2 and the Component Model, such as a Wasmtime that meets the version requirement. The `.wasm` does not depend on the build machine's Linux glibc, nor does it carry Linux `.so` files.

Browser mode also requires deploying:

- The ESM and core Wasm files generated by Jco.
- The application's HTML, CSS, and JavaScript.
- The WASI Preview 2 Shim and Worker Host.

Do not just copy the Jco-generated directory and then double-click the HTML directly. Serve the resources through Vite, Nginx, or another HTTP Server; production deployment also needs correct Wasm MIME type configuration and the CORS/CSP policies used by the application.

## Common Errors

### Required WASI tool was not found in PATH

For example:

```text
Required WASI tool `wasm32-wasip2-clang++` was not found in PATH
```

Add the `bin` directories of the WASI SDK and Wasmtime to `PATH`. In browser mode, also ensure `jco` can be found. Component mode does not require Jco.

### WASI tool is too old

Upgrade to a tool that meets the minimum version on this page. Old WABT, LLVM, or Wasmtime from system package repositories cannot replace the current WASI SDK toolchain.

### TypePHP WASI SDK is missing or ABI-incompatible

Confirm that the PHPX package matching the current TypePHP version is installed, and check:

```bash
test -f "$PHPX_HOME/wasm/wasm32-wasip2/.typephp-wasi-sdk-abi"
test -f "$PHPX_HOME/wasm/wasm32-wasip2/lib/libphp.a"
test -f "$PHPX_HOME/wasm/wasm32-wasip2/lib/libphpx.a"
```

Do not copy `.a` files from a different TypePHP/PHPX version to overwrite these.

### Required WASI tool `wit-bindgen` was not found in PATH

This error only occurs in `mode: library` builds. Install and verify the pinned version:

```bash
cargo install wit-bindgen-cli --version 0.60.0 --locked
export PATH="$HOME/.cargo/bin:$PATH"
wit-bindgen --version
```

If an incompatible version is reported, uninstall the same-named program from other sources, or adjust `PATH` to ensure `wit-bindgen-cli 0.60.0` is found first.

### The browser reports that JSPI is not supported

Upgrade the browser and confirm that `WebAssembly.Suspending` and `WebAssembly.promising` exist. The application must run inside a Worker using a Jco/WASI Host that supports JSPI.

### file_get_contents() requests fail

In Wasmtime, confirm you are using:

```bash
wasmtime -S http app.wasm
```

In the browser, check the CORS, CSP, certificate, and Mixed Content errors in the developer tools. The HTTP API being available does not mean the browser allows access to arbitrary addresses.

### File functions report No such file or directory

In Wasmtime, use `--dir` to pre-open directories and ensure the program accesses Guest paths. In the browser, the filesystem must be configured by the Worker Host; TypePHP does not automatically grant host filesystem access.
