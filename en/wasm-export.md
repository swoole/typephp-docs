# WasmExport Compile-time Attribute

`WasmExport` publishes TypePHP functions as the WIT interface of a WASI 0.2 Component, allowing JavaScript, the Wasmtime Embed API, or other Component Hosts to call TypePHP directly.

It is a compile-time Attribute that only generates WIT, Canonical ABI adapters, and static bindings; it does not look up functions via PHP reflection at runtime. For the namespace rules shared by all built-in Attributes, see [Compile-time Attributes](compile-time-attributes.md).

## First Exported Function

```php
<?php

#[WasmExport]
function add(int $left, int $right): int
{
    return $left + $right;
}

#[WasmExport(name: 'greet-user')]
function greetUser(string $name): string
{
    return "Hello, {$name}";
}
```

When no `name` is specified, TypePHP converts the PHP camelCase name to lowercase hyphenated form; for example, `greetUser` is exported as `greet-user`. An explicit name must be a valid, non-duplicate WIT identifier, such as `load-user`; the name may only contain lowercase ASCII letters, digits, and single hyphens separating words.

`WasmExport` is in the root namespace. In other namespaces write `#[\WasmExport]`, or import it first via `use \WasmExport;`.

## project.yml

Exported functions must be built using WASM library mode:

```yaml
name: calculator
mode: library
wasm: browser
wasm-package: app:calculator@1.0.0
wasm-world: calculator

sources:
  - src

build-dir: build
output: component/calculator.wasm
wasm-browser-dir: generated
```

Configuration meaning:

- `mode: library`: generates a library component called by the Host, without automatically executing `main()`.
- `wasm: component`: only generates the `.wasm` Component, suitable for a custom Host or the Wasmtime Embed API.
- `wasm: browser`: additionally uses Jco to generate browser ESM.
- `wasm-package`: the WIT package, whose format must be `namespace:name@major.minor.patch`.
- `wasm-world`: the WIT world name.

At least one `#[WasmExport]` function must be declared. For the full WASI SDK and browser environment configuration, see [Compiling to WebAssembly](wasm.md).

Library mode also requires `wit-bindgen-cli 0.60.0` to be on the `PATH`:

```bash
cargo install wit-bindgen-cli --version 0.60.0 --locked
wit-bindgen --version
```

It only generates the Canonical ABI bindings for the current application during the build; it is not linked into PHPX or the final `.wasm`. An ordinary command component using `mode: bin` does not need to install it.

## Supported Parameter and Return Types

The current ABI supports:

| TypePHP type | WIT type | JavaScript type |
|---|---|---|
| `bool` | `bool` | `boolean` |
| `int` | `s64` | `bigint` |
| `float` | `f64` | `number` |
| `string` | `string` | `string` |
| `?bool`, `?int`, `?float`, `?string` | `option<T>` | the corresponding type or `undefined` |
| `void` return | `result<_, typephp-error>` | `undefined`, throws on failure |

Parameters and return values must have explicit type declarations. Currently not supported:

- `mixed`, undeclared types, and union types.
- PHP `array`, objects, resources, and callables.
- reference parameters, variadic parameters, and optional parameters with default values.
- returning references, Generators, and class methods.

PHP has no generic parameter syntax such as `array<int>`, so the compiler cannot determine which WIT `list<T>` an `array` should map to. Currently, arrays or dynamic objects need to be encoded as JSON strings:

```php
#[WasmExport(name: 'summarize-users')]
function summarizeUsers(string $json): string
{
    $users = json_decode($json, true, flags: JSON_THROW_ON_ERROR);

    return json_encode(
        ['count' => count($users)],
        JSON_THROW_ON_ERROR | JSON_UNESCAPED_UNICODE,
    );
}
```

```js
const result = await runtime.summarizeUsers(JSON.stringify([
    { name: 'Ada' },
    { name: 'Linus' },
]));

console.log(JSON.parse(result));
```

JSON adds encoding, parsing, and intermediate string allocation overhead, and suits dynamic structures or low-frequency interfaces. Language-level type mappings for WIT `list`, `record`, and object resources are not yet available.

## JavaScript Invocation

The module generated by Jco exports `api.createRuntime()`. A library component has no automatic entry point, so a runtime resource must be created first:

```js
import { instantiate } from './generated/program.js';

const component = await instantiate(null, wasi.getImportObject());
const runtime = await component.api.createRuntime();

try {
    const sum = await runtime.add(20n, 22n);
    const greeting = await runtime.greetUser('TypePHP');

    console.log(sum);       // 42n
    console.log(greeting);  // Hello, TypePHP
} finally {
    runtime[Symbol.dispose]();
}
```

PHP `int` corresponds to a signed 64-bit integer, so JavaScript must pass and receive `bigint`, for example `20n`, and cannot pass an ordinary `20`.

TypePHP exports in the browser are asynchronous JavaScript functions. Even if a function currently only computes CPU data, always use `await`; this allows the function internals to safely call WASI APIs such as time, file, and HTTP that may suspend via JSPI.

## ZendVM Lifecycle

`createRuntime()` initializes the PHP Embed SAPI, the ZendVM, the current application module, and a PHP request, and performs the corresponding MINIT/RINIT. Users should not call the Zend C API directly, and do not need to call MINIT/RINIT themselves.

All export calls on the same runtime share this request:

- RINIT/RSHUTDOWN are not repeated for every call.
- Request-level global variables, static state, and memory pools persist until the runtime is released.
- The current WASI Runtime is NTS, and the same runtime does not allow concurrent or reentrant calls; callers should `await` serially.
- PHP exceptions are converted into WIT `result`, and Jco surfaces the error as a JavaScript exception.
- A Zend bailout puts the runtime into a failed state, and subsequent calls are rejected.

`runtime[Symbol.dispose]()` performs RSHUTDOWN, module cleanup, and PHP Embed shutdown. Do not rely only on JavaScript GC; terminating a Worker directly also does not guarantee that the PHP shutdown callbacks are executed.

## Complete Example

`examples/wasm-hello` in the TypePHP repository demonstrates the complete interaction flow:

1. JavaScript instantiates the Component in a Worker.
2. It calls `api.createRuntime()` to establish a ZendVM request.
3. The page clicks on a PHP extension name.
4. The Worker calls `runtime.getExtensionInfo()`.
5. TypePHP returns a JSON string, and JavaScript parses and renders the extension details.

This example also demonstrates JSPI, HTTP, the file system, time, random numbers, and PHP high-precision types.
