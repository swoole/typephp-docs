# Using TypePHP Dynamic Libraries

TypePHP can compile PHP functions, classes, and C++ `php_*` functions into a dynamic library using `-m lib`, which can then be called directly by other TypePHP projects. This page walks through a complete example of how to create, publish, and use a TypePHP library.

## What you need to publish

A library used by other TypePHP projects typically includes:

| Platform | Required files |
|------|----------|
| Linux | `.stub.php`, `lib<library name>.so` |
| Windows | `.stub.php`, `<library name>.dll`, `<library name>.lib` |

`-m lib` automatically generates `<library name>.stub.php`, which describes the functions and classes provided by the library. Other projects read it at compile time to check the interface and find the library to link.

The `php_<target>_func_decl.h` and `php_<target>_data_decl.h` generated by TypePHP in the build directory are internal files and do not need to be published with the library.

If the library also provides additional C ABI or C++ ABI interfaces, the library author should write and publish the corresponding `.h` files. `.stub.php` only describes the functions that TypePHP PHP code can call.

## Step 1: Create the library project

Create a simple vector library named `prime2`:

```text
prime2/
├── project.yml
└── src/
    ├── math.php
    ├── vector.stub.php
    └── vector.cc
```

### Writing PHP functions and classes

Create `src/math.php`:

```php
<?php

class Counter
{
    public const int STEP = 2;
    public int $value = 1;

    public function add(int $amount = self::STEP): int
    {
        $this->value += $amount;
        return $this->value;
    }
}

function twice(int $value): int
{
    return $value * 2;
}
```

A PHP implementation does not need a separate hand-written stub. The compiler automatically extracts function, class, property, constant, and method declarations.

### Declaring library functions

Create `src/vector.stub.php`:

```php
<?php
function vector_new(int $size, bool $initialValue = false): mixed {}
function vector_get(mixed $vector, int $offset): bool {}
function vector_set(mixed $vector, int $offset, bool $value): void {}
```

Notes:

- Function bodies in `.stub.php` must be empty; the concrete implementation goes in the C++ file.
- Parameter types, return types, and default values are part of the library interface; after changes, both the stub and the dynamic library must be republished.
- Do not add `@import-library` to the local stub inside a library project; its functions are implemented by the current project's C++ code.

### Writing the C++ implementation

Create `src/vector.cc`:

```cpp
#include <phpx.h>

using namespace php;

class VectorBox : public Box {
  public:
    std::vector<bool> values;

    VectorBox(size_t size, bool initialValue) : values(size, initialValue) {}
};

Var php_vector_new(Int size, Bool initialValue) {
    return {new VectorBox(size, initialValue)};
}

Bool php_vector_get(Var vector, Int offset) {
    auto box = vector.toBox<VectorBox>();
    return box->values.at(offset);
}

void php_vector_set(Var vector, Int offset, Bool value) {
    auto box = vector.toBox<VectorBox>();
    box->values.at(offset) = value;
}
```

The C++ function name must prepend `php_` to the PHP function name. The common correspondences between parameters and return values are as follows:

| PHP | C++ |
|-----|-----|
| `int` | `php::Int` |
| `bool` | `php::Bool` |
| `float` | `php::Float` |
| `string` | `php::Str` |
| `array` | `php::Array` |
| `mixed` | `php::Var` |
| `object` | `php::Object` |
| `void` | `void` |

### Configuring the library project

Create `project.yml`:

```yaml
name: prime2
mode: lib
build-dir: build

sources:
  - src
```

`name: prime2` determines the automatically generated `prime2.stub.php` filename and the library name used in the final linking.

## Step 2: Compile the dynamic library

Run in the library project directory:

```bash
tpc project.yml -O2
```

You can also specify the build mode on the command line:

```bash
tpc project.yml -m lib -O2
```

Default output on Linux:

```text
libprime2.so
prime2.stub.php
```

Default output on Windows:

```text
prime2.dll
prime2.lib
prime2.stub.php
```

The `.dll` is the runtime dynamic library, and the `.lib` is the import library used when linking other Windows projects.

## Step 3: Organize the published files

On Linux you can organize as:

```text
prime2-package/
├── stubs/
│   └── prime2.stub.php
└── lib/
    └── libprime2.so
```

On Windows you can organize as:

```text
prime2-package/
├── stubs/
│   └── prime2.stub.php
└── lib/
    ├── prime2.dll
    └── prime2.lib
```

The automatically generated `prime2.stub.php` has `@import-library` at the top. It indicates that all functions and class methods in the file are provided by an external TypePHP library. The library name is derived from the stub filename, so do not rename this file.

When a consuming project compiles this stub, it generates the class registration, property, and constant entities in the current project, but does not generate the `php_*` implementations of the methods; the method implementations are always imported from the `prime2` dynamic library.

Property hooks can also be published together with the class interface. The generated stub preserves the `get`/`set` declarations and removes the concrete code; the consuming project creates the property entities, and the getter/setter implementations are provided by the dynamic library.

### Hiding the library's internal interface

Functions, classes, or methods that are only for internal library use can be marked with `#[NoExport]`:

```php
#[\NoExport]
function normalizeInternalData(array $data): array
{
    // for internal use only within the current library
}

#[\NoExport]
class InternalCache {}
```

The declarations still participate in the current library's compilation and can be called from code within the library, but they do not appear in `<target>.stub.php`, and the corresponding `php_*` symbols are not exported. See [`NoExport` compile-time attribute](no-export.md) for the full function, class, method, and namespace usage.

## Step 4: Using it in another TypePHP project

Assume the application project structure is as follows:

```text
my-app/
├── project.yml
├── src/
│   └── main.php
└── deps/
    └── prime2/
        ├── stubs/
        │   └── prime2.stub.php
        └── lib/
            ├── libprime2.so      # Linux
            ├── prime2.dll        # Windows
            └── prime2.lib        # Windows
```

The application only needs to add the `.stub.php` to `sources` and specify the library directory via `link-paths`:

```yaml
name: my-app
mode: bin
build-dir: build

sources:
  - src
  - deps/prime2/stubs/prime2.stub.php

link-paths:
  - deps/prime2/lib
```

There is no need to configure `link-libs: [prime2]`. After reading the `@import-library` in `prime2.stub.php`, the compiler derives `prime2` from the filename and automatically links that library.

In `src/main.php` you can use it like an ordinary PHP function:

```php
<?php

function main(): void
{
    $vector = vector_new(4);
    vector_set($vector, 2, true);

    var_dump(vector_get($vector, 2));

    $counter = new Counter();
    var_dump($counter->add());
    var_dump(twice(6));
}
```

Compile the application:

```bash
tpc project.yml -O2
```

## Step 5: Make the program find the dynamic library at runtime

A successful link only means the compiler found the library; when running the application, the operating system must also be able to find the dynamic library.

### Linux

During development you can set it temporarily:

```bash
LD_LIBRARY_PATH="$PWD/deps/prime2/lib" ./my_app
```

When publishing the application, you can also install `libprime2.so` into a system dynamic library directory, or configure a suitable rpath for the application. Do not copy only the executable and omit the `.so`.

### Windows

The simplest approach is to copy `prime2.dll` into the directory containing the application `.exe`:

```text
release/
├── my_app.exe
└── prime2.dll
```

`prime2.lib` is only needed when compiling and linking the application; what the application needs at runtime is `prime2.dll`.

## Updating the library interface

When changing function parameters, return types, or default values:

1. Modify the source directly for PHP implementations; for C++ implementations, update the local `.stub.php` and C++ code at the same time.
2. Recompile the dynamic library.
3. Publish the new stub together with the dynamic library.
4. Recompile all TypePHP projects that use the library.

Do not mix a new `.stub.php` with an old `.so`, `.dll`, or `.lib`.

## Compatibility notes

The library and the projects that use it should keep the following environments compatible:

- Same operating system and CPU architecture, for example both Linux x86-64.
- Compatible PHP major version, thread safety mode (ZTS/NTS), and PHPX environment.
- Compatible TypePHP version.
- When using the C++ ABI, compatible compiler and runtime library ABIs.

Different operating systems and CPU architectures require separately compiled and published dynamic libraries.

## FAQ

### Linker reports that `prime2` cannot be found

Check:

- Whether `link-paths` points to the actual library directory.
- Whether the Linux filename is `libprime2.so`.
- Whether `prime2.lib` exists in the Windows library directory.
- Whether you are using the compiler-generated `prime2.stub.php` with `@import-library` preserved at the top of the file.

### Linker reports that symbols such as `php_vector_new` cannot be found

Check the C++ implementation:

- Whether the function name has the `php_` prefix.
- Whether the parameters and return types match the stub.
- Whether the published stub filename matches the library target name.
- Whether the dynamic library was recompiled after modifying the stub.

### The program compiles successfully but cannot find the dynamic library at startup

This is a runtime library search path issue:

- Linux: configure `LD_LIBRARY_PATH`, rpath, or a system dynamic library directory.
- Windows: put the `.dll` in the same directory as the `.exe`, or add it to `PATH`.

### Do I need to publish the generated `func_decl.h` and `data_decl.h`

No. They are internal files of the TypePHP build process, not part of the library's public interface. TypePHP function interfaces are published via `.stub.php`; additional C/C++ interfaces require the library author to provide hand-written `.h` files.
